# Лагуна рыбаков — система анализа изменений

**Команда:** Uyblf  
**Участники:** Зубков Алексей, Громов Иван, Каневских Павел, Бокарев Роман.
**Задача:** сравнить два среза ответов системы принятия решений (СПР), найти изменения на уровне заявок и атрибутов и дать аналитику понятный путь от общего вердикта до причины.

## 1. Описание решения

Проект объединяет обработку JSON-ответов СПР и рабочий кабинет аналитика. На вход подаются два среза одного прогона: `data/BEFORE` до изменения стратегии и `data/AFTER` после изменения. Сервис нормализации приводит вложенные ответы к плоским фактам, сервис сравнения сопоставляет факты по идентификатору заявки и ключу атрибута, а pivot-слой строит агрегаты для отчёта.

В веб-интерфейсе доступны:

- обзор с числом заявок, различий и смен решений;
- создание пользовательской конфигурации с выбором источников, процедур и проверок;
- запуск демо-прогона с неблокирующим журналом этапов;
- отчёт с четырьмя типами изменений: `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_REMOVED`, `SAME`;
- сводная таблица с фильтрами и переходом от агрегата к заявке и атрибуту;
- детальное сравнение `BEFORE_MASTER` и `AFTER_BETA`;
- отдельный отчёт автоматических проверок;
- документация по Docker и контракту пользовательских процедур;
- скачивание автономного HTML-отчёта и README.

## 3. Используемые технологии

- **Python 3.12**, Flask 3.1 и Gunicorn — HTTP-приложение и production-запуск.
- **pandas** — сводные таблицы и работа с витриной фактов.
- **Стандартная библиотека Python** (`json`, `csv`, `pathlib`) — чтение ответов, нормализация и экспорт.
- **HTML, CSS и JavaScript без тяжёлого frontend-фреймворка** — простой читаемый кабинет аналитика с responsive-версткой.

- **Docker и Docker Compose** — воспроизводимое окружение на чистой машине.

Модели машинного обучения и внешние LLM в текущем решении не используются: сравнение выполняется детерминированными процедурами, чтобы результат совпадал с эталоном.

## 4. Данные

Основной источник — выданные JSON-ответы СПР, разложенные по папкам `data/BEFORE` и `data/AFTER`. Один и тот же идентификатор заявки используется как ключ сопоставления. Дополнительные внешние данные не загружаются.

Предобработка выполняется в `src/services/normalize.py`:

1. JSON читается с `utf-8-sig`.
2. Вложенные объекты обходятся рекурсивно.
3. Массивы получают устойчивый `ARRAY_KEY`, поэтому порядок элементов не влияет на сравнение.
4. Технические поля исключаются настройкой `DEFAULTS["exclude"]`.
5. Для чисел при необходимости рассчитывается `ADJUSTED_VALUE` с помощью заданных интервалов.
6. Результат сохраняется в `data/result.csv` с разделителем `;`.

## 5. Архитектура и подход

Полный путь данных выглядит так:

```text
JSON BEFORE + JSON AFTER
          │
          ▼
   normalize_json_files()
          │
          ▼
       result.csv
          │
          ▼
       comparison()
          │
          ▼
    comparison.csv
          │
          ▼
  pivot / Mart / HTML report
```

Идентификатор факта строится из `APP_ID`, `PREFIX`, `CLASS`, `SUFFIX`, `ARRAY_KEY` и `KEY`. Сначала индексируются строки `AFTER`, затем добавляются строки, которые есть только в `BEFORE`. Для каждой пары определяется тип изменения:

- `ATTRIBUTE_NEW` — атрибут появился;
- `ATTRIBUTE_REMOVED` — атрибут исчез;
- `VALUE_CHANGED` — фактическое значение изменилось;
- `SAME` — значения совпали.

Сравнение выполняется по фактическим значениям, а не по бакетам. Это позволяет не потерять небольшие изменения в числовых полях. В интерфейсе длинные операции представлены отдельным журналом этапов и progress bar. Процедуры нормализации и сравнения в пользовательском сценарии выбираются как интерактивный код или файл `.py` с фиксированным контрактом.

## 6. Эксперименты и результаты

Проверены следующие гипотезы:

- сопоставление элементов массива по устойчивому ключу надёжнее сопоставления по позиции;
- разделение `VALUE_CHANGED`, `ATTRIBUTE_NEW` и `ATTRIBUTE_REMOVED` даёт аналитикам понятное объяснение причины;
- отдельный `ADJUSTED_VALUE` полезен для сводных разрезов, но не должен заменять сравнение исходных значений;
- переход от `counts` к конкретной заявке важнее вывода всей плоской витрины на одном экране.

В интерфейсе зафиксирован контрольный сценарий открытого датасета:

| Метрика | Значение |
| --- | ---: |
| Заявок в прогоне | 2 002 |
| Заявок с различиями | 487 |
| Заявок со сменой решения | 126 |
| Фактов в витрине | около 290 тыс. |
| Типов изменений | 4 |

Числа в dashboard используются как демонстрационный контрольный сценарий; при подключении полного набора данных итоговые значения рассчитываются процедурами из `src/services`.

## 7. Инструкция по запуску

### Локальный запуск

Требуется Python 3.12 или новее.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
python src/services/normalize.py
python src/services/comparison.py
python main.py
```

После запуска откройте <http://127.0.0.1:5000>.

### Docker

```bash
docker compose up --build
```

После сборки откройте <http://127.0.0.1:4173>.

Для остановки:

```bash
docker compose down
```

### Повторное воспроизведение отчёта

1. Поместите два среза JSON в `data/BEFORE` и `data/AFTER`.
2. Запустите `python src/services/normalize.py`.
3. Запустите `python src/services/comparison.py`.
4. Используйте `result.csv` и `comparison.csv` в pivot-слое или откройте кабинет.

Конфиги интерфейса в demo-режиме сохраняются в `localStorage`, чтобы сценарий переживал перезагрузку страницы. Для production-хранилища слой сохранения можно заменить на SQLite/D1/Supabase без изменения пользовательского интерфейса.

## 8. Ограничения и дальнейшее развитие

- В текущем прототипе долгий прогон в браузере имитируется, а не запускает Python-процесс из UI.
- Demo-конфигурации и отчёты сохраняются локально в браузере; серверная многопользовательская авторизация и постоянное хранилище требуют отдельного backend-слоя.
- Для полного открытого датасета стоит добавить фоновую очередь задач, поток обновлений прогресса и индексы по `APP_ID`/`PATH`.
- Следующий шаг — подключить пользовательские `.py`-процедуры через sandbox с ограничением ресурсов и журналированием версии кода.
- Для production-проверки стоит добавить автоматические тесты контракта процедур, тесты на неизвестный прогон и нагрузочный замер сводной таблицы.
